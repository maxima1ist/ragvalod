## 1. Описание проекта

Разрабатывается система личного чат-бота с использованием **Retrieval-Augmented Generation (RAG)**, полностью развёртываемая локально в Docker-контейнерах на машине с NVIDIA GeForce RTX 3070 (8 ГБ VRAM). Система должна обеспечивать:

- Автоматический сбор данных из **Notion** (с возможностью расширения на другие источники).
- Построение и обновление векторной базы данных (локально, в отдельном контейнере).
- Двухступенчатый поиск релевантных документов: быстрый bi-encoder (векторный поиск) и точный cross-encoder (реранкер).
- Генерацию ответа с использованием открытой LLM, запускаемой локально через движок инференса (vLLM) - в отдельном контейнере, либо с возможностью переключения на внешний API.
- REST API (FastAPI) для взаимодействия с системой, позволяющее управлять параметрами поиска и генерации.
- Мониторинг и оценку качества (опционально с Langfuse и LLM-as-a-judge).

Проект должен быть масштабируемым: начальная реализация на Docker Compose, но архитектура должна позволять переход на Kubernetes для горизонтального масштабирования.

## 2. Архитектура и компоненты

Система состоит из следующих микросервисов (каждый в своём контейнере):

1. **Ingestion Service** – Python-сервис для сбора данных из источников (Notion и др.), чанкинга, генерации эмбеддингов и загрузки в векторную БД. Запускается по требованию (не постоянный сервис).
2. **Vector Database** – Qdrant (в контейнере) для хранения эмбеддингов и метаданных.
3. **RAG Orchestrator** – основной FastAPI-сервис, реализующий бизнес-логику: эмбеддинг запроса, двухступенчатый поиск, формирование промпта, вызов LLM.
4. **Inference Server** – vLLM, предоставляющий OpenAI-совместимый API для локальной LLM (Mistral-7B / Llama-3-8B в 4-bit). Может быть заменён на прокси для внешнего API.
5. **Monitoring (опционально)** – Langfuse для трассировки, логирования и оценки.

**Оркестрация:** Docker Compose для разработки и локального запуска. В будущем – Kubernetes.

**Инструменты:**
- **LlamaIndex** – для индексации и поиска (data layer).
- **LangChain** – для оркестрации пайплайна RAG, формирования промптов, интеграции с LLM.
- **FastAPI** – для REST API.
- **Sentence Transformers** – для эмбеддингов (bi-encoder).
- **Cross-encoders** – для реранкинга (например, BAAI/bge-reranker-base).
- **vLLM** – для инференса LLM с поддержкой GPU.
- **Docker / Docker Compose** – контейнеризация.

**Требования к GPU:** 
- 8 ГБ VRAM достаточно для 7B-модели в 4-bit (AWQ/GGUF) с контекстом до 4096 токенов.
- Для эмбеддингов и реранкера можно использовать CPU, но для ускорения – GPU (можно разделять через CUDA_VISIBLE_DEVICES).

**Шаг 3.2:** Реализовать эмбеддинг запроса: использовать ту же модель, что и при индексации (загружается один раз при старте приложения).

## 4. Детали конфигурации и переменные окружения

**Ingestion Service:**
- `NOTION_TOKEN` – токен интеграции Notion.
- `QDRANT_HOST` – hostname Qdrant (в compose: `qdrant`).
- `QDRANT_PORT` – 6333.
- `EMBEDDING_MODEL` – имя модели (например, `intfloat/multilingual-e5-small`).
- `CHUNK_SIZE`, `CHUNK_OVERLAP`.

**RAG Orchestrator:**
- `QDRANT_HOST`, `QDRANT_PORT`.
- `EMBEDDING_MODEL` – та же модель, что и при индексации.
- `RERANKER_MODEL` – например, `BAAI/bge-reranker-base`.
- `LLM_PROVIDER` – `local` или `openai`.
- `LLM_ENDPOINT` – URL vLLM (например, `http://vllm:8000/v1`) или внешний API.
- `OPENAI_API_KEY` – если используется внешний.
- `LANGFUSE_PUBLIC_KEY`, `LANGFUSE_SECRET_KEY` – если используется.

**vLLM:**
- `MODEL_NAME` – полное имя модели на HuggingFace.
- `MAX_MODEL_LEN` – 4096.
- Дополнительные флаги (см. документацию vLLM).

## 5. Критерии успеха для каждого этапа

- **Этап 0:** Docker Compose успешно поднимает все контейнеры, приложение доступно по портам.
- **Этап 1:** Ингест загружает данные из Notion, чанки и эмбеддинги корректно сохраняются в Qdrant.
- **Этап 2:** Поисковый запрос возвращает чанки с высоким сходством (проверка вручную).
- **Этап 3:** FastAPI отвечает на `/health` и `/generate`; ответ содержит осмысленные чанки и сгенерированный текст.
- **Этап 4:** Локальная LLM генерирует ответы с приемлемой скоростью (не менее 20 токенов/сек) и качеством.
- **Этап 5:** Langfuse отображает трассировки, оценки записываются.
- **Этап 6:** Новые источники данных подключаются без изменения основного кода.
- **Этап 7:** Приложение может быть развёрнуто в K8s с несколькими репликами без сбоев.

## 6. Рекомендации для AI-агента

- Все сервисы писать на Python 3.10+ с использованием `poetry` или `pipenv` для управления зависимостями.
- Код должен быть покрыт type hints и документирован (docstrings).
- Использовать `python-dotenv` для загрузки переменных окружения.
- Все конфигурации должны быть вынесены в `.env` файл.
- Логировать все ошибки и информационные сообщения с использованием `logging`.
- Для HTTP-запросов использовать `httpx` или `aiohttp` (асинхронно).
- В FastAPI использовать `async` def для эндпоинтов, чтобы не блокировать событийный цикл.

## 7. Примечания по производительности и ограничениям

- При использовании RTX 3070 (8 ГБ) и модели 7B в 4-bit, контекст 4096 токенов + батч из 1 запроса должны работать без OOM. Если возникает нехватка памяти, уменьшить `max-model-len` до 2048 или использовать модель меньшего размера (Phi-3-mini).
- Для реранкера использовать CPU (если памяти мало) или загружать на GPU только при необходимости.
- Векторный поиск в Qdrant использует HNSW, время поиска ~10-50 мс для 50 чанков.
- Рекомендуется кешировать эмбеддинги запросов, если одинаковые запросы повторяются.
